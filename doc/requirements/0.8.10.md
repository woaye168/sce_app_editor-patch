# 0.8.10 需求文档：AI 易用性「轨道化」——让正确路径成为阻力最小路径

> 状态：**需求已收集，待评审排期**。
> 来源：2026-09-03~04 test_res002 全量测试（2 小时，AI 全程自主执行）的真实使用反馈 +
> 任务后三轮深度复盘对话。测试报告：test_res002 `.bgd/test/report.md`；
> 逐轮执行记录：`.bgd/test/checklist.md`。
> 本文档全部内容来自**真实使用中踩过的坑**，非想象需求。

## 背景：这次全量测试暴露的不是「能力缺失」而是「默认路径错误」

0.8.0~0.8.9 的能力面在 2 小时高强度真实使用中**全部可用**（find_ui/tap/drag_ui/eval/run_scenario/多人 player 定向/set_pause/分玩家日志/审计日志无一失效）。但过程中反复出现同一模式：

> **工具给了两条路，AI 选了快的那条，而快的那条恰好绕过了产品真实路径。**

具体表现：背包/商店/锻造/技能的逻辑层测试全部用 `lua.eval` 直发协议完成（快、确定、可统计），导致**背包 UI 在整整一轮测试里从未被真实打开过**——用户在旁观时亲眼看到「锻造提示在弹但背包界面根本没开」才发现。这不是 AI 性格问题，是任何 AI 面对「eval 一行搞定」vs「拖拽 20 步」都会做的选择。

**设计哲学（本轮最高约束）**：无法确保每个 AGENT 的性格与习惯，只能从工具链自身想办法——**让正确的路恰好是阻力最小的路**。不依赖 AI 自觉，不依赖提示词教育，靠工具结构与默认行为兜底。

## 需求清单

### R1 eval 逃生舱的边界显性化（description 双向界定）

**问题**：`lua.eval` 的 description 只说了能干什么（逃生舱、danger），没说不该干什么。AI 在真实需求压力下会拿它驱动业务协议（`protocol.send_to_server(P.Req_*)`）绕过全部 UI 验证。

**方案**（description 改写，零代码逻辑变更）：

```
lua.eval — 游戏 VM 逃生舱（danger 级，兜底通道）。
仅用于：① 无对应工具的运行时状态读取/断言；② 测试探针安装（链式包装
base.proto 捕获消息）；③ 统计性验证（概率/分布采样）；④ 构造 UI 无法到达的
边界态（满包/非法参数/断档）。
禁止用于：能用 find_ui/tap/drag_ui/key_down 完成的 UI 操作——UI 链路必须走
真实操作验证，eval 绕过 UI 的测试不算 UI 已测。
```

**配套**：eval 返回的 hint 增加反问引导——「该操作有对应 UI 入口吗？有则用 lua.tap 走真实路径」（hint 随能力集同步发版的既有纪律覆盖）。

### R2 run_scenario 的定位修正与「取证三段式」步骤类型

**定位修正（2026-09-04 实测纠正，推翻旧结论）**：`run_scenario` 适合**定稿后归档复跑**
（一把跑完已验证的路径），**不适合探索期排错**——复杂验证用场景脚本反而更难定位
失败点，短命令逐段迭代更快（checklist.md L379 实测记录）。libs/AGENTS.md「一把跑完」
的表述需修正为「定稿归档用 run_scenario，探索期用短命令」。

**问题**：正确的测试姿势（操作 → 截图 → 状态断言 → 日志锚点）是复盘后才总结出来的，
新上下文的 AI 不会天然这么做。截图是「无预设的观察」，断言是「有预设的验证」——
只有后者会漏掉「没想到要查的东西」（本轮 BUG-04 日志刷屏就是这么漏的：
**是 tail 末尾意外撞到的，不是 match 查到的**——工具找不到不是问题，
没有「看看整体健不健康」这个动作才是）。

**三层断言结构**（每条用例的完整验证）：UI 呈现（截图/视觉通道）+ 数据状态（eval 读）+
服务端行为（日志锚点）。本次测试绝大多数只有后两层。

**新增步骤 op**（服务于「定稿归档」定位，让定稿脚本天然带取证）：

| op | 语义 | 解决 |
| --- | --- | --- |
| `verify_ui {q, scope?, tag?}` | find_ui + capture_ui + 返回「UI 存在且长这样」一步完成 | 「UI 存在性验证」从三个动作变一个 |
| `check_logs {match?, errors_zero?: true}` | 查日志 + errors 段必须为 0 的断言（默认开） | AI 不再需要「记得查 errors」 |
| 场景结束自动附件 | run_scenario 跑完自动附「期间日志摘要：新增行数/errors/warnings/top 重复行」 | 刷屏类问题（BUG-04 型）天然暴露 |

### R3 取证覆盖率自检（证据计数器）

**问题**：本轮 Round 1 全程零截图，没有任何机制提醒。「画面没看过」应该是一个可检测的状态，而不是依赖用户旁观发现。

**方案**：`get_status` / run_scenario 结束返回附 `evidence` 段：

```json
"evidence": { "captures": 0, "ui_ops": 47, "eval_ops": 12 }
```

当 `eval_ops` 远大于 `ui_ops` 且 `captures == 0` 时 hint 显性提示：「本会话大量 eval 但零截图——若测的是 UI 功能，画面取证缺失」。实现 = 计数器，成本极低。

**与 skills 的分工**：正确姿势已由三个工序 skill 承载（sce-test-feature 的完成定义四条
明确「至少一张截图」为必做项）——计数器是**兜底自检**：AI 没加载 skill 或漏执行时，
工具层还能兜住。skill 管「该怎么做」，计数器管「没做对时提醒」，两层不冲突。

### R4 关键 UI 操作可选视觉回执

**方案**：tap/drag_ui 加可选 `snapshot=true`：操作后自动 crop 该控件区域截小图存证，返回路径。文本断言（expect）只能验「文本变了」，验不了「画面看起来对」；视觉回执让「每次关键操作留证据」成为默认动作而非额外负担。crop 局部图成本可控。

### R8 视觉通道常态化（能力打通，零代码）

**问题**：当前模型 `Read` 工具不支持读图——AI 发现自己「看不了图」后会把整个视觉通道
划掉（本轮 Round 1 零截图的部分原因）。实际存在替代通道（具体形态因模型/平台而异：
mmx VLM / Claude vision / GPT-4o 等）——但 AI 不会天然把「我需要看」和「有这么个通道」
联系起来。

**方案**：
1. `capture_game`/`capture_ui` 返回的 hint 补一句：「读图走视觉通道」，
   常见为 image-understanding / vision 技能），模型 Read 不一定支持图像」——**泛化表述，
   不绑定具体工具名**
2. **批量读图作为标准收尾动作**：场景跑完后对全部截图批量过一遍（视觉通道），
   把「没想过要查的东西」兜住——这是探索型测试的关键补漏机制（详见 R2 背景）
3. **像素级判定纪律**（实测教训）：视觉模型在降采样图上会误判行列数与遮罩有无——
   网格数/压暗判定/精确色值一律用**区域平均亮度数值比对**，视觉模型只用于「这是什么/
   大概什么样」的语义级判断。此纪律已收录于 sce-test-feature 与 sce-debug-issue 工序，
   capture 系 hint 同步提醒。
