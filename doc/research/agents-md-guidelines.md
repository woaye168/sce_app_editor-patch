# AGENTS.md 编写规范研究（2026-08-19）

> 来源：agents.md 官方规范与最佳实践、Matt Pocock《A Complete Guide To AGENTS.md》、GitHub 2500+ 仓库实证分析、社区经验文（agentsmd.io、掘金/博客园多篇）综合整理。
> 用途：本仓库（及兄弟仓库）AGENTS.md 的编写与维护准则。

## 定位：它是什么

- **「给 AI 看的 README」**（A README for agents）。2025-08 由 OpenAI/Amp/Google/Cursor/Factory 联合发起的开放标准，Linux 基金会托管，6 万+ 仓库采用。
- 它是**唯一每轮对话都会被完整加载到上下文顶部**的项目文件——LLM 无状态，AGENTS.md 就是项目的「外部记忆 / 操作手册」。
- 与 README.md 分工：README 面向人（介绍/上手），AGENTS.md 面向 AI（工程约定/命令/红线）。

## 核心约束：指令预算（最重要的一条）

- AGENTS.md 的**每一个 token 每次请求都会加载**，无论与当前任务是否相关。
- 前沿思考型模型大约能稳定遵循 150–200 条指令；系统提示已占掉约 50 条。**文件越大，留给干活的预算越少，且指令遵循率随条数线性下降**。
- **过时信息 = 每轮投毒**：人看到过时文档会怀疑，AI 会自信地照做。版本流水账、易漂移的具体路径是最快腐烂的内容。
- 结论：**Less is More**。核心文件控制在 ~200 行内（社区经验值 <300，理想 <60 的也有）；只放全局通用、持久稳定的信息。

## 放什么（WHAT / WHY / HOW + 边界 + 索引）

1. **一句话项目定位**（角色设定锚点）+ 技术栈要点（非默认的才写，如包管理器不是 npm）。
2. **可复制粘贴的命令**：构建/检查/测试/发布，给文件级小命令优先（快速反馈），全量构建标注「谨慎使用」。
3. **HOW 的关键机制**：AI 自己推断不出来、不写就会做错的事实（如「私有仓库 asset 必须走 API 下载」「静态 require 构建期改写」）。**描述能力而非结构**——少写易变的具体文件路径，多写稳定的领域概念与机制。
4. **硬边界（红线/Don'ts）**：明确「绝不能做什么」比「应该怎么做」更有效（权限边界：哪些操作要先问）。
5. **文档索引（渐进式披露）**：细节文档给路径让 AI 按需自取（doc/research、doc/requirements、skills 知识库），不内联细节。

## 不放什么（反模式清单）

- **版本更新记录/编年史**：「0.5.3 起 / 0.6.8 新增」这类内容属于 Release notes 与 doc/requirements，AGENTS.md 只写**当前事实**。
- **详细代码风格指南**：交给 linter/formatter（AI 当 linter 用成本高效差）。
- **大段代码块与全量 API 文档**：会腐烂；用文件路径引用代替（且路径要少而稳）。
- **自动生成的内容**：工具生成的「什么都有」全是噪音，手写、从实际错误中迭代。
- **特定任务才用的信息**：违背「全局通用」原则的一律去细节文档。

## 维护方式

- **从实际错误中迭代**：AI 犯了错 → 加一条针对性规则；定期整体梳理，删掉已被代码自愈的规则。
- **与代码同 PR 更新**：改机制的同一次提交更新对应描述，防止漂移。
- **活文档**：每次大改后问一句「这段还成立吗」，腐烂的内容比没有更糟。

## 兄弟仓库落地要点（本次整改依据）

| 反模式 | 处置 |
| --- | --- |
| 版本号编年史（0.5.x 起/新增/细节）散布全文 | 全部去掉版本号，折叠为当前事实描述 |
| 每个机制都带「某版本引入」的叙述 | 删除；历史留 doc/requirements |
| 超长的单段机制描述 | 压缩到「AI 做错会踩坑」的密度，细节指到 doc/research |
