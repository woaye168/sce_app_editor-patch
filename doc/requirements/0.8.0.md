# 0.8.0 需求与方案：MCP 上下文防爆 + UI 可观测/可交互闭环

> 状态：**已实现，真机验证通过（2026-08-29）**；待交付时打 tag 走 CI
> 背景：AI 经 MCP 排障时两大痛点——① 工具返回无尺寸护栏，大响应（截图读图/日志/桥能力返回）撑爆上下文；② AI 只能「看」不能「动」，无法对游戏 UI 做点击/输入等交互，闭环调试（查询 → 操作 → 验证）断在操作环节。
> 目标：让 AI 具备低成本的 UI 闭环调试能力：**find_ui 定位 → click/input 操作 → capture/probe 验证**，全程上下文可控。
>
> **迭代中追加的 8 条用户留言已全量并入本轮**：① MCP 易用性自改进；② 补按下/松开/移入（press_ui/release_ui/hover_ui——hover 经研究证实引擎层不可注入，诚实报错）；③ 日志 errors 自动上浮 + 同条收纳×N；④ catalog 瘦身（剔除 svc.FileSystem 等 AI 自己能干的能力 287→247 条）+ find_ui 别名增强；⑤ danger 默认放行（danger_allow → danger_deny 反转）；⑥ widget 可控性契约文档（cgui_mcp.md）；⑦ run_scenario 批量场景执行；⑧ 超 500 行模块拆分（core.lua 拆 dbg.lua/remember.lua、dbg_bus 拆 dbg_commands、editor.rs 拆 logs.rs、桥 main.lua 拆 ui_loop.lua）。

## 需求清单

### R0 前期研究（最高优先级，R2/R3 的前置闸门）

R2/R3 的 API 形态完全取决于引擎 UI 机制的实测结论，**先研究后定实现**。研究结论落盘 `doc/research/ui-reflection.md`。

**静态研究已得结论（2026-08-28，读 cgui 源码 + api13 全包 Lua 源码 `D:\sce_open\api-13\2026_08_27`）**：

- 游戏 UI 是 **cgui 即时模式**（封装引擎 `imgui`）：控件每帧重建，无持久控件树，点击 = 引擎 imgui 每帧产出交互状态（`on_real_click`），widget 层检测到后调业务回调（[control.lua](file:///c:/Users/woaye/Documents/SCE%20Projects/test_res002/.bgd/libs/client/cgui/widget/control.lua#L83-L86)）。
- 因此游戏侧**不存在「找到控件再触发它的 on_click」的持久对象**，反射点应在**引擎输入/imgui 状态层**（注入指针位置+点击，下一帧 imgui 自然命中分发）。
- 编辑器 UI（xdeditor `base.ui`）是持久控件树，与游戏 UI 是**两个世界**——get_game_view_rect 只证明了编辑器侧可达。
- **Q1 重大突破——引擎原生多 VM 消息总线已实锤**（用户线索 `lobby.vm_name()`/`send_luastate_broadcast` 挖通）：
  - 运行时存在命名 lua VM：`StateEditor` / `StateGame` / `StateApplication`（`__lua_state_name` 全局变量 + `lobby.vm_name()`，见 script/199/common/base/game.lua:91-93、lib_gamechat、defaultui 大量用法）；
  - 原生 `lobby` 模块（`require '@base.base.lobby'`）提供**跨 VM 通信全套 API**：`lobby.send_luastate_broadcast(name, data)` 广播 + `lobby.register_luaState_event(name, fn)` 接收（lib_lobby/170/ui/src/event/global_event.lua:56 等大量实例），另有 `lobby.app_lua` 跨 VM 可调用函数注册表（script/199/common/base/lobby.lua:6 + ad.lua:41 `co.wrap(lobby.app_lua.play_custom_ad)()`）；
  - **意义**：若 PIE 调试时游戏 client 跑在 StateGame 且 lobby 总线可用，则在游戏框架 client 侧注册一个 `bgd_*` 事件接收器 = 编辑器→游戏 VM 的命令通道，Q1 从「是否互通」变成「总线在 PIE/编辑器上下文是否可用」的纯实测问题。

### R1.5 响应引导设计（P0，随 R1 同改 mcp.rs）

**原则：工具返回本身承担「引导 AI 下一步」的职责**——AI 必读工具返回（AGENTS.md 可能被截断/不读），这是最可靠的行为引导位。三条纪律：

1. **成功响应带 `hint` 字段**（一行、建议口吻、上下文相关）：把 find→click→capture 闭环写进每次返回。如 find_ui 返回带「可用 lua.click_ui 点击该控件，或 capture_game(crop=此rect) 局部验证」；capture_game 返回带「用 Read 查看；只看局部可带 crop 重截」。
2. **错误响应必须 actionable**（现有实践的固化）：报错必带下一步操作引导（现有「请先 editor_start」模式扩展为全员约定）。
3. **固定纪律放工具 description**（tools/list 常驻上下文），动态指引放 hint，两者搭配不重复。

**明确不做**：不追 MCP `outputSchema`/structuredContent（2025-06-18 协议）——消费方是 AI IDE，读 JSON 文本与读 schema 能力相同，协议升级收益小且有兼容风险；引导价值由 hint 文本承载即可。

hint 约束：**一行、可选、不重复 description 已有内容**，否则自身成为上下文噪音；R1.1 截断提示（「已截断，请用更精确参数重试」）即 hint 模式的一种，统一风格。**版本一致性**：hint 不得引用尚未上线的能力（如 R3 未发布前 find_ui 的 hint 不提 click_ui）——hint 文本随能力集同步发版，防止把 AI 引导到不存在的工具。

### R2 运行时 UI 查询（P1，R3 前置）

**能力**：新增桥能力 `lua.find_ui`——按名称/id 查询 UI 控件，返回逻辑坐标矩形，供 AI 精确定位后接 click/crop/probe。

**实现形态依 R0 Q1/Q3 结论二选一**：

- 若游戏侧可从编辑器上下文直达：编辑器侧 `handlers.find_ui` 直接查询；
- 若 VM 隔离：游戏框架（cgui）加调试钩子，每帧沉淀 `id → {rect, visible}` 快照表，编辑器侧经可达通道查询——**cgui 控件有业务 id**（`button(label, fn, id)`），按 id 查询反而比按名更稳。

**编辑器侧 UI（base.ui 持久树）查询为附带收益**：同 handler 一并支持（调编辑器本身界面时用）；**此部分不依赖 R0 结论，可先行交付**（get_game_view_rect 已证明可达）。

**落地三处**（Gateway 架构，不加 MCP 工具，经 invoke_capability 触达）：

1. `patches/xdeditor/bgd_mcp_bridge/main.lua` 加 `handlers.find_ui`（+ 可能的框架侧钩子）；
2. `csharp/make_catalog/Program.cs` StaticEntries 加 `Entry("lua.find_ui", "lua", "find_ui", "array", "read", [...])`（read 级）；
3. `csharp/bgd_mcp_bridge/annotations.json` 加搜索标注（别名：坐标/控件/查找）。

**设计约束**：

- 坐标一律逻辑坐标，与 crop/probe/click 参数同系，AI 零换算；
- **结果条数硬上限 20 + truncated 标记**——查询工具自身也不能爆上下文；只支持按名/id 查询，不做全树 dump；
- **快照钩子惰性开启**：cgui 每帧沉淀 id→rect 是常驻开销，默认关闭，仅在 PIE 调试且收到首次查询/交互命令时开启（或随 bgd 调试配置开关），退出调试自动关闭。

### R3 UI 交互操作（P1，本期核心新增）

**需求**：AI 能对调试中的游戏 UI 做交互，最小集：点击 / 文本输入。

**实现路线（已定：纯 Lua UI 事件/输入层反射，不做 Win32 注入）**：

游戏 UI 是 cgui/imgui 即时模式（R0 静态结论），反射点不在控件对象而在**输入/imgui 状态层**：

| 路径 | 思路 | 说明 |
| --- | --- | --- |
| A. imgui 输入注入（首选） | 脚本注入指针位置 + 按下/抬起，下一帧 imgui 自然命中分发，走完整真实交互链路（悬停/按下/抬起/on_real_click） | 最真实等价人工操作；可行性 = R0 Q2 |
| B. cgui 框架调试接口（备选） | cgui 钩子直接按 id 触发 widget 的交互回调（绕过引擎输入） | 不依赖引擎注入能力；但绕过真实事件链，可能与真实行为有偏差；VM 隔离时需配合 Q1 通道 |

**落地形态**（write 级能力，具体 API 形态依 R0 结论定稿）：

- `lua.click_ui {id}` / `lua.click_at {x, y}` —— 按 id 点击（查快照取 rect 中心）/ 逻辑坐标点击
- `lua.input_text {id, text}` —— 输入框文本输入（视 R0 Q4 结论决定是否本期）

**安全边界（天然隔离，无需额外防护）**：交互经 VM 总线注入到**游戏 VM 的 imgui 输入层**，作用域物理上限于游戏 UI——编辑器 UI 不在该 VM 内，不存在误触编辑器菜单的可能。

**验收闭环**：find_ui 定位 → click/input 操作 → capture_game(crop) 验证界面变化，全程无需人工、无需前台焦点（纯 lua 层，后台可交互）。

## 真机验证记录（test_res002，2026-08-29）

**R0 研究结论**（全部实测，落盘 doc/research/ui-reflection.md + lua-vm-bus.md）：

- Q1：lobby 跨 VM 总线在 PIE 下双向打通（StateEditor↔StateGame ping-pong）；`__lua_state_name` 实测为 nil（旧知识有误，已修正文档），判 VM 用 `lobby.vm_name()`。
- Q2：SCE imgui ≠ Dear ImGui，输入为拉取式（`imgui.state()`），脚本层**无输入注入 API** → R3 走路径 B（cgui 框架反射，回调直调 + state 注入兜底双路径）。
- Q3：`core.finish()` 为快照沉淀挂点；`imgui.ui_get_rect(st.id)` 取 rect，÷scale 得逻辑坐标。
- Q4：input 走 widget 注册的 `input` 回调直设文本；hover 引擎层不可注入 → hover_ui 诚实报错。

**R1 护栏**：32KB 截断护栏（单测）；capture crop+max_width（crop=find_ui rect 截出正好是商店按钮图，900 宽）；match 正则过滤（真机 0_49 日志文件 1973 条刷屏错误收纳为 2 条 ×1521/×449）；get_events 本地切片 50 条（单测）。
