## 问题归因（13:07/13:47 留言要求：不只修问题，要分析为什么会误判）

### 归因 1：「面板没打开却说打开了」——注入成功 ≠ 业务生效

- **现象**：AI 调 tap/click_ui 成功（返回「注入已受理」）后断言面板已开，用户指出实际未开。
- **根因**：操作类命令只有「受理」语义没有「结果」语义；验证要等下一帧后再 find/assert，
  两次往返的摩擦导致跳验。toggle 类入口盲点还会反关（已知坑）。
- **修复（工具化验证）**：`tap`/`click_ui` 新增 `expect`/`expect_absent` 参数——
  延迟 3 帧后在快照断言文本出现/消失，把「操作+验证」复合成一次调用。
- **发现的桥缺陷（顺带修复）**：桥 ui_loop.lua 的 handlers 用**参数白名单**转发，
  游戏侧新增的 expect 参数被桥静默吞掉（游戏侧收不到，自然不验证——第一版实测 verified
  字段缺失即此因）。**白名单转发违背「桥保持薄转发」原则**：每个游戏侧新参数都要改桥 +
  重启编辑器。已改为**全参透传**（参数校验是游戏侧命令自己的职责）。

### 归因 2：「总爱截原图」——局部截图的摩擦在工具侧

- **现象**：验证单个 UI 时习惯截整个视口原图，撑上下文。
- **根因**：`capture_game` 无 crop 时默认截全视口；拿 crop 坐标要先 `find_ui` 再手抄
  rect——两次往返 + 手抄坐标易错，摩擦导致直接截全图。
- **修复**：`run_scenario` 新增 `capture_ui {q, pad?, max_width?}` 复合步骤
  （find→rect→crop 截图一步）；`capture_game` 无 crop 时 hint 引导 capture_ui。
- **AI 自律**：看单个 UI 一律 capture_ui / crop；只有看整体布局才截全图，且调小 max_width。

### 归因 3：「click_ui 打到不存在控件」——过期 id + 错误引导不到位

- **现象**：多次 `控件不存在：cgui_bench/overlay/dropdown_list/3`。
- **根因**：dropdown 浮层全局一份、关闭即销毁、菜单项 id 带序号——AI 用了上一次
  find_ui 的过期 id 快照。旧错误文案（「先 find_ui 查询」）没指出更优路径。
- **修复**：错误文案按场景分流——浮层项 id 指 `lua.pick {q,item}`；通用指
  `lua.tap {q}`（文本复合命令内部自动重查，免疫 id 失效）。

### 归因 4（13:47）：默认值静默生效会误导判断——举一反三

- **问题**：`capture_ui max_width 默认 640`、`capture_game 默认 1280` 这类默认值
  **静默降采样**，AI 拿缩放图做像素级判读（缝隙/对齐/字体）会得出错误结论而不自知。
- **原则**：默认值本身没错，**静默**才是问题。凡改变结果语义的默认值，响应必须显式回显
  生效值与后果。
- **修复**：截图响应新增 `natural_width/natural_height/downscaled` 回显，被降采样时附
  note「像素级判读请显式调大 max_width」。
- **存量默认值审计结论**（抽查）：find_ui 20 条上限有 `truncated` 标记 ✅；tap 多命中
  有「另有 N 个候选」note ✅；run_scenario 2KB/32KB 截断有显式提示 ✅；
  get_game_logs tail_lines=0 只回文件信息有 hint 引导 ✅——均符合「默认值可见」纪律。
