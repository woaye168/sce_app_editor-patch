# 0.8.7 v1 评审意见

> 评审对象：[0.8.7.md](0.8.7.md)（MCP 模拟多人调试）。逐条编号，格式沿用 0.8.5 评审惯例。
> 本评审的关键立场：**凡是需求里写了「经桥 C# SendEvent」「隐含自动切焦」这类
> 未经实测的实现承诺，一律降级为「待验证假设」**，先把实验做掉再定方案。

1、
【需求】R1「内部经桥 C# `SendEvent('CS_muti_debug', json)` 走官方处理器」
【评审】这里有个事实性松动：研究结论说桥 C# 的 SendMenuCommand 是对**原生事件
`EditorMainTitleMenuBar`** 的 SendEvent（EditorBridge.cs:132-155），而
`CS_muti_debug` 是 xdeditor Lua 侧 `eventMgr:register_event` 注册的事件——这两条
是不是同一个 EventManager 总线、C# 侧能否对任意字符串事件 SendEvent，**没有核实**。
而且别忘了：桥 Lua 补丁本来就跑在 StateEditor 同一个 VM 里，`require 'ui.menu_bar'`
后 `.debug_save_as` 和那个 :1752 处理器的全部依赖（obj_manager 读数编三键）都在
同 VM 可达——**纯 Lua 同 VM 复刻/直调极可能是更短路径**，根本不用跨 C#。
请开发第一步先做「桥 Lua 同 VM 直接调通 muti_debug」的 spike，C# 事件通道只在
纯 Lua 路径被证实不可行时才启用。需求文档应把 R1 改成「两条候选路径 + spike 决策点」，
而不是直接钦定 C# 路径。

2、
【需求】R1 参数 `no_compile?=bool`（等效 use_last_debug_info）
【评审】`use_last_debug_info` 的前置是 `last_debug_path` 已存在（上次调试目录）。
编辑器重启后首次多人调试传 no_compile 会发生什么？需求没写。请补：前置不满足时
的行为定义（报错 or 自动回退全量），且这个回退逻辑要与 start_debug 的
「restart_last_debug 失败回退 full」语义对齐，不要发明第二种回退风格。

3、
【需求】R1 `auto_open_slots`「等价对话框那个 ContentDialog 确认，写数编 Game/opened_slots」
【评审】写数编 = **改用户项目文件**，这是比「拉起调试」重得多的副作用。三个问题：
① MutiDebugWindow.cs:779-821 具体写了哪些键、有没有连带写别的（比如槽位启用还
涉及 player_setting 其他字段），需求里只有一句「等价」，开发时必须逐字段核实；
② 这个写操作会不会触发项目「有未保存改动」的脏标记，干扰用户后续保存/版本管理；
③ 默认值必须是 false（不授权就不写），且 MCP 返回里要显式回显「本次写入了哪些
数编键」。请把这三点补进 R1 验收。

4、
【需求】R1 默认策略「数编 type='user' 的前 N 个 opened 玩家」
【评审】**Team 字段的缺省策略整段缺失**。对话框里选人时 Player/Team 是
GetPlayerAndTeam() 返回的绑定对，选「空」= int.MaxValue。我们直调时 Team 缺省
给什么？给错编队，test_res002 这种有组队玩法的地图调试出来的局就是错的。
请补：Team 缺省 = 数编 player_setting 里该玩家的默认编队（开发时核实字段名），
而不是留空/MaxValue 了事。

5、
【需求】R1 风险 4「默认给 0/2/4/6s 递增 delay 作为缺省策略」
【评审】这是拍脑袋。官方对话框 Delay 默认就是 0，官方自己对「同帧拉起有时序竞争」
没有任何提示。请改成：**先实测 4 客户端 Delay=0 同帧拉起是否稳定**（连跑 5 次看
客户端上线率），不稳定才引入递增 delay，并把实测结论记进 research。不要为一个
未验证的竞争预设全局默认。

6、
【需求】R2「MCP 新工具 start_mp_debug」
【评审】**「恒定 15 工具」是写在 AGENTS.md 里的 MCP 护栏设计**，加一个就变 16。
要么打破恒定（那就同步改 AGENTS.md 表述并说明理由），要么走能力目录
（lua.mp_debug_start，invoke_capability 触达）。我的倾向：多人调试是与 start_debug
同级的核心调试入口，值得静态工具，打破恒定——但这是**需要用户拍板的决策点**，
需求文档应显式列出这个决策而不是默认加工具。同理 mp_client_list/switch 的归属
（静态工具 vs lua.* 能力）也要一并定：我的建议是 list/switch 走能力目录
（与 lua.find_ui 等同族），MCP 静态面只加 start_mp_debug 一个。

7、
【需求】R2 未定义与现有调试状态的互斥
【评审】已在单人调试中（GamePlayInEditor 在线）再调 start_mp_debug 会怎样？反过来
多人局中调 start_debug 呢？请补前置定义：建议 start_mp_debug 检测到任何
GamePlayInEditor* 槽位在线时**先自动 stop 再拉起**（与人工操作习惯一致），
并在返回里回显「已先停止上一轮调试」。不定义就是埋雷。

8、
【需求】R1/R2 无失败检测与清理
【评审】start_debug 有 WaitStatusAsync 轮询（120s 超时），start_mp_debug 也必须有：
轮询各目标槽位 is_plugin_ui_loaded，部分上线/全部超时要有明确错误返回（哪个槽位
失败、官方处理器有没有把某行 Enabled 置 false——CS_muti_debug 处理器失败时只是
往 info 列表写错误，**MCP 调用会假成功**，风险 3 已经提了但 R1/R2 的任务卡里没有
对应的验收动作）。请补：拉起结果返回逐槽位上线状态数组，失败槽位附原因。

9、
【需求】R3「经 lobby 广播 ping 收集各 VM vm_name」进 get_status
【评审】get_status 是同步 RPC，广播收集是异步的——**等多久？** 等收集窗口（500ms？）
get_status 延迟变差；不等则首次调用返回空。建议：桥侧维护「最近一次 ping 收集结果」
缓存（调试期间周期性 refresh 或事件驱动），get_status 读缓存零延迟；mp_client_list
才做实时收集。这个设计细节请在 dev 文档定稿，需求里先把「同步接口不得阻塞等广播」
立为约束。

10、
【需求】R4「顺带 reconnect 处理暂停态」
【评审】不要预设官方没做的事。官方 tab 切换（set_game_ui_focus 路径）对暂停态
客户端本来是什么行为？先实测：暂停某客户端 → 切走 → 切回，是否自动 reconnect。
官方已处理我们就啥也不加；官方不处理、且暂停态导致截图黑/命令无响应，再补
reconnect 并写明理由。请把「顺带 reconnect」从需求里删掉，改为「实测暂停态切换
行为后按需补充」。

11、
【需求】R5「client 截图隐含自动 switch→等帧→截→（可选）切回」
【评审】两个没讨论的点：① AI 连续截 4 个玩家 = 编辑器 tab 连续跳 4 次，**用户
正在看编辑器时体验很糟**，要不要一个 `focus=false` 选项（只截不切，接受后台 tab
可能停渲的黑图风险）还是统一切焦？这依赖风险 1 的实测结论，但选项形态可以先定；
② 切焦后「等帧」等多久？引擎渲染帧率不固定，等帧策略（固定 500ms？等两帧？）
要实测给出下界，太慢会拖垮 scenario。请补进 R5。

12、
【需求】R6「client 缺省 = 现状广播先到先得（向后兼容）」
【评审】**协议兼容性想得不够**。多人局里旧框架的 dbg_bus（不认 target 字段）收到
带 target 的 cmd 会全员应答；新 dbg_bus 收到旧 ui_loop 不带 target 的 cmd 也会
全员应答——而回执配对在多人下同 id 多答互相覆盖的问题**在缺省路径依然存在**。
请补：dbg_bus 握手加协议版本（ping 应答带 proto_version），ui_loop 感知对端版本，
旧对端 + 多人局 = 定向命令明确报错「游戏侧框架过旧，需更新框架重新构建」，
不允许静默退化出互相覆盖的混乱行为。错误信息要能引导用户（更新框架+build+
restart），沿用现有 timeout 文案的引导风格。

13、
【需求】R5/R6 的 q 参数联动缺失
【评审】capture_game 的 `q`（find_ui 定位局部截图）= 先走 lua.find_ui 拿 rect 再裁。
多人下 find_ui 不走定向 VM，q 截图截的就是「先到先得那个 VM」的 UI——**q 必须
与 client 组合使用才有意义**。请补进 R5 验收：q+client 组合链路（定向 find_ui →
定向视口裁剪）跑通；q 不带 client 且多人局时返回告警hint。

14、
【需求】全文缺失：**get_game_logs 的多人适配**
【评审】这是排障刚需，漏了。多人 PIE 下客户端日志写到哪？编辑器 debug_client_info
面板按 userID 归类（log.set_log_handler 带 userID），但 MCP get_game_logs 读的是
<运行根>/logs/ 文件——多人实例是混写一个文件（带 userID 前缀？）还是分文件？
先实测，然后：混写 → get_game_logs 加 client/userid 过滤参数（match 正则层面就能做）；
分文件 → LOG_SOURCES 源枚举扩展。请补一条需求（建议进 P1）。

15、
【需求】R7 run_scenario 步骤级 client 字段
【评审】方向对，但补一个一致性约束：scenario 步骤串行执行，若步骤 3 对 client1
tap、步骤 4 对 client2 截图（隐含切焦），**切焦动作与 vp 注入目标 VM 之间有没有
耦合**？（vp 点击坐标基于哪个视口换算？）如果 vp 坐标换算是焦点视口感知的，
client 切换步骤间需要强制等帧/重查坐标。请在 R7 验收里加「跨 client 交替操作
20 步场景脚本跑绿」这一条，把耦合问题逼出来。

16、
【需求】验收环境前提全文未提
【评审】test_res002 的数编里有几个 type='user' 的玩家？opened_slots 开了几个？
Game.user_ids 够分吗？CS_muti_debug 处理器对「找不到第 N 个玩家 ID」是直接
return 整局不起的（menu_bar.lua:1769-1775）。请补一条 P0 前置任务：检查并按需
配置验收地图的玩家设置（≥2 user 玩家 + 槽位启用 + user_ids 充足），否则验收
第一步就卡死。

17、
【需求】风险 3「桥侧需能取到失败信号（监听 add_info_list 或预校验后拒绝）」
【评审】监听 add_info_list 是事后被动且脆弱（靠文案匹配？），**预校验才是正路**：
桥 Lua 同 VM 能读数编三键（opened_slots/player_setting/user_ids），发 CS_muti_debug
之前先自己跑一遍 :1752 处理器的校验逻辑，不通过直接拒绝并返回具体原因——官方
处理器的降级路径根本不触发。这样风险 3 整个消解。请把「预校验」从风险项提升为
R1 的明确实现要求。

18、
【需求】文档形态
【评审】沿用 0.8.5 第 22 条结论：本版本定稿后同样拆 **0.8.7.md（需求：任务清单+
验收+决策备查）+ 0.8.7_dev.md（开发文档：架构图/寻址协议精准定义/签名总表/
spike 结论记录位）**。当前单文件里「研究结论」节已经长得像 dev 文档了，拆分后
研究结论进 dev，需求文档只留任务与验收。老规矩：每个字有真实作用，空话一字不写。
