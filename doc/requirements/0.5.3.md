## 需求（原始）

0.5.3 解释解决前述场景一的体验完整性。

其实 sce_app_editor-patch 的 bgd_mcp_bridge，在本套工具链中有两个场景：

1. 场景一：编辑器的基础功能控制，让 AGENT 基于 bgd_sce_tools、bgd_sce_framework 框架开发，拥有完整的开发调试链路。
2. 场景二：编辑器的完整拟人控制，让 AGENT 可以在编辑器中进行完全的拟人控制，主要用来改星火编辑器可视化开发的老项目。

场景二暂时放到一边，等后续再考虑。当前主要解决「场景一」的体验完整性。

场景一的常用 MCP 命令应该是这几个：

1. 启动星火编辑器（需要讨论实现方案：需要根据项目组装启动命令；要考虑此时编辑器都没开启，现有的 MCP 服务都没有开启）
2. 关闭星火编辑器（需要讨论实现方案）
3. 启动调试（已有 tool。使用 restart_last_debug，更快，跳过编辑器的一遍编译构建，但又能载入最新的 lua 代码）
4. 停止调试（已有 tool。stop_debug）
5. 获取日志（需要讨论实现方案：返回最新日志文件的路径还是目录？MCP tools 的参数怎么设计？总之考虑 AGENT 调用、节省流程、方便调试、AI 友好）
6. 发布项目（已有 tool。MCP 现有菜单命令可以发布项目）
7. 截取游戏画面（需要讨论实现方案，截取调试状态下的游戏画面）

日志包括：

- 游戏客户端日志（游戏调试运行产生）：`D:\sce_online\logs\lua`，最新的 `lua-game-*.log`
- 游戏服务端日志（游戏调试运行产生）：`D:\sce_online\logs\server`，最新的 `core-game-server-*.log` 和 `lua-game-server-*.log`
- bgd_csharp 的 MCP 日志：`D:\sce_online\logs\bgd_csharp`（`bgd_csharp-*.log`、`audit-*.log`）

此外顺手修复的小问题：

1. 在 bgd_sce_tools 里切换游戏项目之后，再次打开 sce_app_editor-patch 界面也显示了新的项目路径，但是此时（unwatch 模块）获得的项目路径是上一次的（现在的逻辑必须要重新取消勾选再勾选 unwatch 才会刷新注入的 `_project_root.lua`）。
2. sce.deps.json 里 bgd_mcp_bridge.dll 始终登记为 1.0.0，看看有没必要让版本号跟着本插件走。
3. csharp/make_catalog/Program.cs 里有「D:/sce_online」「D:\sce_online」的硬编码，是否可以优化（举一反三排查其他硬编码）。
4. 星火编辑器 xdeditor 包从 160 升级到 169 后出现「○ 未应用 xdeditor（编辑器界面）[v169]（无此版本插槽文件，将跳过）→ 检测到部分库未应用」。优化流程：如果发现新版本解码后的 lua 与我们已有 slots 版本的解码后 lua 完全一致，该 slots 文件直接复用；如果不一致，继续走备份+解码流程，并尝试通过模式匹配进行运行时插槽注入。总之不能因为编辑器包升级一点就导致插槽流程整体不可用。精准插槽是为了避免出错，但不应成为更新和使用的瓶颈。

## 现状基线（调研结论）

- **bgd_mcp_bridge（0.5.0 Gateway 架构）已具备**：`start_debug` / `restart_last_debug` / `stop_debug` 直暴露元工具；`invoke_capability` 可调 `cmd.发布/发布项目` 等全部菜单命令；`get_status` / `get_events` / `set_suppress` 完备。服务随编辑器进程存亡（编辑器关闭即下线）。
- **致命缺口**：bgd_mcp_bridge 是编辑器进程内服务，**编辑器未启动时不存在任何 MCP 服务**——「启动编辑器」无法由它自己承担。必须有一个**编辑器进程外的宿主**承担生命周期类命令。
- **编辑器启动命令已实证**（0.5.0 自测自修轮沿用）：
  `<运行根>/星火编辑器.exe -inner -winui_material_editor -winui_resource_store -editor_api_version=<api> -file_path="<项目>/project.sce"`
  其中运行根（如 `D:/sce_online`）与 api 版本均可由项目路径经 locate 链推导（map_settings.json → tsconfig.json typeRoots → 编辑器根 → 上两级即运行根）。
- **日志全部落盘在 `<运行根>/logs/` 下**（lua/、server/、bgd_csharp/），读日志**不需要编辑器在线**。
- **server_info 已返回 pid**（McpServer.cs），外部拿到 pid 即可实现关闭编辑器。

## 总体方案：双端 MCP，单一入口聚合

```
AI 客户端（Trae 等，stdio MCP 配置一次）
   │
   ▼
bgd_sce_tools mcp（新增：stdio MCP 聚合服务，编辑器外常驻能力）
   │── 本地直接实现：editor_start / editor_stop / get_logs / capture_game
   │── 在线检测：读 <运行根>/logs/bgd_csharp/port 文件 → ping 127.0.0.1:<port>/mcp
   └── 在线时透传 bgd_mcp_bridge：start_debug / stop_debug / publish_project / get_status / invoke_capability
            │
            ▼
   bgd_mcp_bridge（现有，编辑器进程内 HTTP/MCP，127.0.0.1:39177+）
```

**关键决策与理由：**

1. **MCP 服务宿主定稿：挂在 bgd_sce_tools 上，不挂 sce_app_editor-patch**。职责划分：
   - **sce_app_editor-patch = 一次性打补丁工具**：应用内核补丁 + 勾选模块后，日常不再打开。
   - **bgd_sce_tools = 日常 MCP 入口**：新增 `bgd_sce_tools mcp` stdio 子命令作为 AGENT 的唯一 MCP 配置项，由 MCP 客户端按需拉起进程（标准 stdio MCP 生命周期），**无需打开任何 GUI**。只要内核补丁已打上、bgd_mcp_bridge 模块已启用，MCP 链路即完整可用。
   - **编辑器侧 HTTP 桥随编辑器启动自动开启**：因为 bgd_mcp_bridge 模块默认勾选（见 F5），每次 editor_start 拉起的编辑器自带进程内服务。
2. **双端分工**：
   - bgd_sce_tools mcp（编辑器外）：editor_start / editor_stop / get_logs / capture_game 本地实现 + 在线透传。Trae 等只支持 stdio 的客户端天然适配；AI 只配这一个 server 即拿全 7 个命令；编辑器不在线时透传类命令返回明确错误「编辑器不在线，请先 editor_start」。
   - bgd_mcp_bridge（编辑器内，现有）：能力目录与菜单命令执行体，基本不动。
3. **bgd_sce_tools 同步暴露同名 CLI 子命令**（`editor start/stop`、`logs`）。符合 bgd_sce_tools AGENTS.md「CLI 是功能验证唯一可信方式」的硬性约定，人类与脚本也可直接用。
4. bgd_sce_tools 需内置一份**轻量 locate 链**（map_settings api_version + tsconfig typeRoots + api_pak_version.json → 运行根/version 目录）。逻辑与 sce_app_editor-patch 的 locate.rs 同源，但两仓库独立发布，不做跨仓库引用，各维护一份（逻辑仅 ~50 行，接受重复）。

## 七大命令细化

### 1. editor_start（新增，bgd_sce_tools 本地实现）

- **参数**：`project_path`（可选，缺省取 bgd_sce_tools 当前项目）；`wait_online`（bool，默认 true）；`timeout_ms`（默认 120000）。
- **实现**：
  1. 幂等检查：读 port 文件 → ping `/mcp` initialize，已在线则直接返回现状（不重复拉起）。
  2. locate 链推导运行根与 api 版本 → 组装启动命令（见「现状基线」的实证命令）。
  3. exe 定位：`<运行根>/<编辑器exe名>`。**exe 名走 bgd_sce_tools 应用设置**：新增设置键 `editor_exe_name`，默认 `星火编辑器.exe`（用户可能改过 exe 名，`setting set editor_exe_name <名字>` 可覆盖）；exe 不存在时报明确错误并提示该设置项。O1 据此定稿关闭。
  4. `CreateProcess` 拉起（detached），随后轮询 port 文件出现 + MCP 握手成功，返回 `{ pid, port, mcp_url, elapsed_ms }`。
  5. 进程起来了但 MCP 超时未上线：返回部分成功 + 排查提示（bgd_mcp_bridge 模块是否勾选、编辑器是否被升级覆盖了补丁、bgd_csharp 日志路径）。**不返回假成功**。
- **边界**：项目未打过补丁/未勾选 MCP 桥时，editor_start 只能保证拉起编辑器，明确提示 MCP 不可用。

### 2. editor_stop（新增，bgd_sce_tools 本地实现）

- **定稿：直接结束进程，不做优雅退出**（O2 据此关闭）。场景一服务代码开发，源码最新性由 bgd_sce_tools build/watch 保证，与编辑器内「是否保存」无关；菜单退出会引入保存确认等官方交互弹窗，徒增复杂度。
- **实现**：
  1. 取 pid：在线时 `server_info.pid`（port 文件 → /rpc server_info）；离线/无 port 文件时按 exe 路径匹配进程列表。
  2. `taskkill /PID <pid> /T /F` 直接强杀（必须带 /F——不带 /F 的 WM_CLOSE 会触发编辑器保存确认弹窗导致挂住）。等待进程消失确认结果。
  3. 找不到进程即返回「编辑器未在运行」（幂等成功）。
- **返回**：`{ stopped: true, pid }`。

### 3. start_debug（透传，语义调整）

- 透传到 bgd_mcp_bridge。按需求定稿：**默认走 `restart_last_debug`**（跳过编辑器编译构建、载入最新 lua——与 bgd_sce_tools build/watch 的产出衔接，这正是场景一的日常高频路径）。
- 失败语义为「无上一次调试版本」时自动回退 `start_debug`（全量）。
- 参数可加 `full: bool`（默认 false）强制全量调试。
- 前置约定：lua 代码最新性由 bgd_sce_tools 的 build/watch 保证（AGENT 链路：改码 → watch 已同步 → restart_last_debug）。

### 4. stop_debug（透传，现有）

- 直接透传 bgd_mcp_bridge `stop_debug`，不变。

### 5. get_logs（新增，bgd_sce_tools 本地实现）

- **定位**：读磁盘日志，**不要求编辑器在线**（崩溃后查日志是核心场景，必须离线可用）。
- **参数**：
  - `source`：`client | server | bridge | all`（默认 `all`）
  - `tail_lines`：int，**默认 0——只返回文件路径与文件信息，不返回任何日志内容**（防止爆 AGENT 上下文；AI 拿到路径后自行 Read 按需分段看，或显式传 `tail_lines` 取末尾内容）
  - `project_path`：可选，同上缺省规则
- **返回**（AI 友好，一次拿全）：

```json
{
  "logs": {
    "client": { "path": "D:/sce_online/logs/lua/lua-game-20260818-1200.log", "size": 12345, "created": "...", "modified": "...", "lines": 1234 },
    "server": {
      "core": { "path": ".../server/core-game-server-*.log", "size": 0, "created": "...", "modified": "...", "lines": 0 },
      "lua":  { "path": ".../server/lua-game-server-*.log", "...": "..." }
    },
    "bridge": {
      "main":  { "path": ".../bgd_csharp/bgd_csharp-*.log", "...": "..." },
      "audit": { "path": ".../bgd_csharp/audit-*.log", "...": "..." }
    }
  }
}
```

- **文件信息**：`path`（最新文件全路径）、`size`（字节）、`created` / `modified`（创建/更新时间）、`lines`（总行数，流式计数不整读）；`tail_lines > 0` 时额外附 `tail` 内容。
- **最新文件判定**：mtime 优先，文件名日期后缀做注释性校验；目录不存在/无文件时该条目返回 `null` 并附说明（如「未产生过调试日志」），不报错。
- **截断保护**：显式取 tail 时单文件字节上限（如 64KB），超出截断并标注 `truncated: true`。
- **结论**：返回**最新文件路径 + 文件信息**，不返回目录（目录对 AI 无行动价值，路径可自取）；日志内容由 AI 按需自取，默认零内容。

### 6. publish_project（透传，现有能力包装）

- 透传 `invoke_capability: cmd.发布/发布项目`。
- **注意点**：
  - `Publish` 关键词命中 danger 分级，需在 `<运行根>/logs/bgd_csharp/config.json` 的 `danger_allow` 放行（文档写明配置示例）。
  - 发布是长耗时操作：透传时放大超时；完成/失败感知方式列入**实测研究任务 R1**（事件流 or 轮询状态+日志关键字，实现轮实测确认后定稿）。
  - 发布有官方流程弹窗风险：透传前自动 set_suppress（与 start_debug 同款纪律）。

### 7. capture_game（新增，先调研后实现）

- **目标**：截取调试状态（PIE 内嵌窗口）的游戏画面，返回给 AI 查看。
- **接口先行**：`capture_game()` → `{ path, width, height }`（图片落盘到 `<项目>/.bgd/log/screenshots/`，MCP 返回路径由 AI 自行 Read；或评估直接返回 MCP image content）。
- **候选实现路线**（按调研优先级排序；均为**实测研究任务**，实现轮逐条实测验证，打通一条即可）：
  - a. 引擎/编辑器自带截图能力：反编译检索 CppInterface / DI 服务中 Capture/Screenshot/ReadPixels 类导出（svc/cpp 通道直接可用则最优）。
  - b. bgd_mcp_bridge 进程内对 GamePlayInEditor 槽位窗口 PrintWindow（D3D swapchain 内容可能黑屏，需实测）。
  - c. 外部 Windows Graphics Capture 截编辑器窗口的游戏视图区域（bgd_sce_tools 侧实现；最通用但最重，需定位游戏视图矩形）。
  - ~~d. 游戏侧调引擎截图 API~~ **已排除**（评审结论：不可行/不可靠，且不应与游戏 API 混合）。
- **验收宽松**：先打通任意一条；黑屏/区域定位问题单列后续迭代。

## 四个小修复

### F1：unwatch 注入的项目路径随项目切换自动刷新

- **问题**：`_project_root.lua` 只在勾选模块时注入；bgd_sce_tools 切项目后重开本应用，UI 已是新项目路径，但编辑器库里的注入文件仍是旧路径。
- **方案**：`refresh()` 成功定位后，扫描**已启用且 `inject_project_root=true`** 的模块，读取其 `_project_root.lua`，与当前项目根（归一化正斜杠）比对；不一致即原子重写，并记日志 + 状态栏提示「检测到项目切换，已自动更新模块注入的项目路径（重启编辑器后生效）」。
- 复用 modules.rs 现有写盘函数（抽出为 pub 供调用），幂等，内容一致不写盘。

### F2：bgd_mcp_bridge.dll 版本号跟随插件版本

- **方案**：
  1. csproj 加 `<Version>0.0.0-dev</Version>` 占位（与 Cargo.toml 同款约定）；CI release.yml 构建时 `-p:Version=<tag去v>` 注入（McpServer.Version 已读 InformationalVersion，server_info 自动带出版本）。
  2. bridge_deploy.rs 的 `LIB_KEY` 由 `env!("CARGO_PKG_VERSION")` 生成（`bgd_mcp_bridge/0.5.3`），assemblyVersion/fileVersion 用 `<major>.<minor>.<patch>.0`。
  3. **undeploy/restore_deps 兼容旧版本**：摘除时按 `bgd_mcp_bridge/` 前缀匹配 targets/libraries 两处全部条目（而非仅当前版本键），保证跨版本升级后旧登记被清干净。
- **收益**：sce.deps.json 里能看出部署的是哪个版本；`needs_redeploy` 的「内容不一致才重写」逻辑不变，升级后自动换登记键。

### F4：插槽版本漂移三级回退（内核改造）

编辑器升级包版本后（如 xdeditor 160→169），`apply` 不再「无插槽即跳过」，按三级回退：

1. **精确匹配（现行）**：`slots/<pkg>/<版本>/` 存在 → 整树字节级复制，不变。
2. **同内容复用**：无精确版本时，取**最近低版本** slots 目录，按其 manifest 逐文件校验——
   - make_slots 生成插槽时同步产出 `slots/<pkg>/<ver>/slot.manifest.json`：记录每个插槽文件的 `{ rel路径, kind(slot入口注入|unlock解锁转换), source_sha256(解码+GBK→UTF-8 后的官方源文本哈希) }`。
   - 运行时：对新版本包内对应文件执行同款「解密 → GBK→UTF-8」得到源文本，与 manifest 的 source_sha256 比对；**全部一致**则判定「上游该文件未变」，直接复用旧版本 slots 文件（复制内容落盘，非引用）。
3. **运行时模式注入**：哈希不一致时，对新版本解码文本**现场执行注入变换**（insert_slot 顶层 return 前插槽 / transform_unlock 解锁行转换）——
   - 把 make_slots.rs 的注入逻辑**下沉为 src/core/slot_inject.rs**（单一事实源），make_slots 工具与运行时内核共用同一份实现。
   - 注入后校验标记在位（INJECT_MARK / UNLOCK_MARK）；锚点匹配失败（如找不到顶层 return、无解锁行）则该库明确报错：「v169 源码结构变化，自动注入失败，请重跑 make_slots 人工固化」。

### F5：补丁模块默认勾选外置配置 + bgd_mcp_bridge/unwatch 转为默认勾选

- **目标**：内核补丁一次应用后，MCP 链路（bgd_mcp_bridge）与解除监听（unwatch）开箱即用，日常只需启动 bgd_sce_tools（MCP 入口）+ editor_start，不再需要打开 sce_app_editor-patch 手工勾选。
- **方案**：
  1. **默认勾选配置外置**：模块清单的 `default_enabled` 不再散落在 modules.rs 的 `builtin_modules()` 代码里，改为仓库内一份配置文件（如 `patches/modules.json`，编译期 include_str! 嵌入，与 patches/ 目录同级管理），声明各模块 id/pkg/名称/描述/默认勾选；源码调整默认值只改这份配置。`deploy_bridge_dll` / `inject_project_root` 等声明一并迁入。
  2. **默认勾选调整**：`bgd_mcp_bridge` 与 `unwatch` 改为 `default_enabled: true`（menu_bgd 保持默认开启）。
  3. **注意**：unwatch 声明了 `inject_project_root`，首次应用内核时 `apply_defaults` 路径需要能拿到 project_root 完成注入（apply_all 本就以 project_root 定位，天然具备，顺路传入即可）。
